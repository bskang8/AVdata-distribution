## 전체 코드흐름 개관 — 무엇을 불러오고·정리하고·분석해 결과를 내나

**한 문장:** 서로 다른 두 분포를 만들어 맞대는 게 전부다 — **P_ext**(외부 공공통계로 조립한
*현실 주행 노출*) vs **P_self**(우리 10만 클립의 *보유 분포*). 둘을 비교해 과수집·시급을 재고
(§9), 빈도로 안 잡히는 **위험**축을 손모델로 얹고(§10·외삽), 결론이 손값에 흔들리는지 확인한다(§11).

```
 [외부 공공 API]                                  [보유 10만 클립 · phase0]
  KMA ASOS ──fetch──▶ raw/kma ┐                    odd_final 태그(road_type·weather…)
  KTDB itmsh ─fetch─▶ raw/ktdb┘                           │
        │  recon.py     (샘플 게이팅: 이 소스로 §2 설계표(아래 8블록)를 채울 수 있나 → SUPPORTED/HAND_ANCHOR)
        ▼  transcribe_* (등급→road_type 매핑 · (월,시) 집계 → 실값)
   sources/*.csv ──loader.py(계약검증 합=1)──▶ {블록별 조건부 확률표}
        │                                                  │
        ▼  compose.py                                      ▼  pself.py
   층화혼합 w(s)×∏블록, 손앵커 marginalize            phase0 crosswalk 재집계(독립 fog)
   = P_ext  현실 노출(신뢰 4축)                       = P_self  우리 데이터 분포(결합)
   → output/P_ext.json                                → output/P_self.json
        └────────────────────┬─────────────────────────────┘
                             ▼  analyze.py
              §8 누적절단(핵심 운행영역) · §9 P_ext↔P_self 대조(과수집 r≫1 / 시급)
                        → output/analysis.json
                             │
      criticality.py  §10 손 위험모델(published 배수) × P_self coverage → criticality.json
                             ▼
      extrapolate.py  §10+ 이웃 확률외삽 → 미관측 위험을 수집갭 vs 희소(합성)로 분리 → extrapolation.json
                             │
      validate.py §11.1 앵커 assert(게이트)   ·   sweep.py §11 민감도(결론 강건성) → sweep.json
                             │
                    run_all.py 가 위 전 단계를 의존순서로 오케스트레이션
```

**여기서 "표"란? — 8개 조건부 확률표(=블록)** (recon이 채울 수 있나 게이팅하는 대상):

| 블록(표) | 정의 | 담당 소스 |
|---|---|---|
| P1_weather | P(weather \| 월,시) | KMA |
| P1_fog | P(안개 \| 월,시) | KMA |
| w_vkt | P(road_type) | KTDB |
| w_hourly | P(시각 \| road_type) | KTDB |
| P4_speed | P(speed \| road_type,weather) | 손앵커 |
| P3_agent | P(참여자 \| road_type,시) | 손앵커 |
| P3_density | P(혼잡 \| road_type,시) | 손앵커 |
| P5_lighting | P(밝기 \| road_type,시) | 손앵커 |

- **이 표들은 어디서 왔나(근거):** 데이터에서 *도출*한 게 아니라 **design.md §2 의존 그래프**로
  **명시(specify)**한 것 — 인과 메커니즘·물리·법(예: 고속도로 보행자=0)·PEGASUS taxonomy가
  "어느 부모가 어느 블록을 조건화하는지"를 정한다. recon은 이 **구조를 만들지 않고**, 실데이터가
  각 표를 채울 수 있는지 **검증·게이팅만** 한다(recon.py 첫머리: "구조를 만들지 않고 검증·축소만").
- compose(§7)는 이 8표를 층 w(s)로 가중혼합해 P_ext를 조립한다. 즉 **recon이 게이팅한 그 표들이
  곧 loader가 계약검증하고 compose가 소비하는 재료**다.

**입력 소스가 실제로 주는 정보** (전체 추출 실적은 RESULTS §2):

| 소스 | API/엔드포인트 | 가져오는 정보(필드) | 커버리지 | 만드는 블록 |
|---|---|---|---|---|
| **KMA ASOS** | apihub `kma_sfctm2`(시간자료) | 시각 `TM`·기온 `TA`·**강수 `RN`**·**시정 `VS`**(+관측소 `STN`) | 2022~2024 전일·전시간·전국 관측소 (2.5M행) | `P1_weather`=P(맑음/비/눈 \| 월,시), `P1_fog`=P(시정<1km \| 월,시) |
| **KTDB itmsh** | data.go.kr `KictTmsStat/itmsh_yearly` | 지점·방향별 **시간대별 연간교통량**(`time_type1..24`)+`total_count`, 도로등급(`dtype`) | dtype **1 고속·2 일반국도만**(3 지방도·5 국지도는 502) | `w_vkt`=P(road_type) 구성비(등급별 total_count), `w_hourly`=등급별 시간형상 |

- weather/fog는 KMA 수치를 **규칙 분류**(강수>0&기온≤0→눈 / 시정<1km→안개)해서 확률표로.
- w_vkt/w_hourly는 KTDB **관측교통량을 정규화**(등급 구성비·시간대 share)로 — 연장가중 VKT 아님.
- **API 미사용**: KASI(밝기)·KoROAD(보행)·용량편람(V/C)·등급속도 = 손앵커 4블록(데이터로 못 얻는 축).

**transcribe_* — raw 원자료를 "표의 실제 숫자"로 채우기**

recon이 "채울 수 있다"고 게이팅한 표에, raw를 실값으로 옮겨 `sources/*.csv`를 만든다. raw는
아직 표 모양이 아니라(낱개 관측이거나 기관 이름) 두 종류의 변환이 필요하다:

- **집계(aggregation)** — KMA: `raw/kma/asos_hourly.csv`의 **낱개 시간관측 250만 줄**(tm·ta·rn·vs)을
  (월,시) 칸으로 몰아넣고 분류·확률화. (`transcribe_weather.py`)
  ```
  raw (낱개 관측, 관측소×매시간):
    202201150800, ta=-2.3, rn=-9.0(무강수) →  1월8시·맑음
    202301150800, ta= 1.2, rn= 0.5        →  1월8시·비    (강수>0 & 영상)
    202401150800, ta=-2.0, rn= 0.4        →  1월8시·눈    (강수>0 & 영하)
       ⋯ "1월 8시" 칸에 3년×전국 관측소 ≈ 8,900개가 쌓임
              ↓ 그 칸에서 맑음/비/눈 개수 세고 합=1로 정규화
  weather_P1.csv:   1,8,clear,0.9375     ← 8,900개 중 93.8%가 맑음
                    1,8,rain,0.0450
                    1,8,snow,0.0175
  ```
  즉 **낱개 관측 수천 개 → "그 칸의 확률" 한 세트**로 접는다(288칸 = 12월×24시 전부).

- **매핑(mapping)** — KTDB: raw의 **기관 등급 이름**을 우리 ODD 값으로 이름 바꾸고
  (mapping.yaml §5-3) 교통량을 구성비로 정규화. (`transcribe_vkt.py`·`transcribe_hourly.py`)
  ```
  raw/ktdb/vkt_sample.csv:            sources/vkt_weight.csv:
    grade,share            ──매핑──▶    road_type,vkt_share
    고속도로,0.41465                     highway,0.41465
    일반도로,0.58535                     national_road,0.58535
  ```
  이름만 바꾸는 게 아니라, **여러 기관 등급이 한 ODD 값으로 합쳐지기도** 한다 —
  예: 지방도+국가지원지방도 → 둘 다 `rural`이면 share를 **합산**(§5-3). w_hourly도 같은 매핑으로
  `고속도로,8,0.0552 → highway,8,0.0552`처럼 시간대 형상을 옮긴다.

즉 세 관문의 역할이 갈린다: **recon**="채울 수 있나?"(판정) → **transcribe**="실제로 채운다"
(raw→sources 실값) → **loader**="채운 게 규칙 지키나?"(조건별 합=1 검증). 손앵커 4블록은 raw가
없어 transcribe 대상이 아니다(sources 값이 손지정).

**단계별 한 줄** (입력 → 하는 일 → 출력):

| 단계 | 입력 | 하는 일 | 출력 |
|---|---|---|---|
| `fetch_*` | 공공 API | 원자료 조달 | `raw/` |
| `recon` | raw 샘플 | 블록별 게이팅(채울 수 있나) | `recon/` |
| `transcribe_*` | raw | 등급→road_type·(월,시) 집계·전사 | `sources/*.csv` |
| `loader` | sources | 계약검증(조건별 합=1) | 블록 확률표 |
| `compose` | 블록표 | 층화 VKT-가중 혼합·정확 enumerate, 손앵커 marginalize | **P_ext**(4축) |
| `pself` | phase0 클립 | crosswalk 재집계(fog 독립·unknown 제외) | **P_self**(결합) |
| `analyze` | P_ext·P_self | §8 핵심영역 + §9 과수집/시급 대조 | `analysis.json` |
| `validate` | loader·compose | §11.1 앵커 assert(틀리면 중단) | (게이트) |
| `criticality` | 손 배수·P_self coverage | §10 위험 랭킹 + 수집 사각지대 | `criticality.json` |
| `extrapolate` | criticality·이웃 coverage | §10+ 미관측을 수집 vs 합성으로 분리 | `extrapolation.json` |
| `sweep` | compose·criticality | §11 손값 ±30% 흔들어 강건성 | `sweep.json` |

**핵심 개념 3가지** (검토 시 놓치면 안 될 틀):
1. **두 분포의 출처가 다르다** — P_ext=외부통계 조립(우리 데이터 무관), P_self=우리 클립. §9는
   이 둘의 *간극*이다.
2. **신뢰 4축만 비교** — 손앵커(speed·agent·density·lighting)는 compose에서 marginalize →
   P_ext는 `{road_type, weather, fog, road_surface}`만. 그 밖은 §10 위험모델·§11 스윕이 담당.
3. **빈도 ≠ 위험** — §8/§9는 *빈도*(노출), §10 criticality는 *위험*(심각도). 최종 수집타겟 =
   빈도 핵심영역 ∪ 위험 사각지대.

### E1 · pself / analyze §9 — national_road self=242가 진짜인가 (검증 대기)

- **질문:** r=0.03("국도 심각 과소") 헤드라인의 유일 근거 카운트 `242`가 실제 부족인가,
  태거 오분류 **아티팩트**인가.
- **왜(레버리지):** §9의 가장 크고 실행가능한 발견이 이 한 숫자에 통째로 걸림. 게다가
  242 = 전체 클립의 **0.24%**로, 한국에 국도가 흔한 것 치고 비현실적으로 작다.
- **코드흐름:**
  ```
  phase0 태거 road_type(odd_final)
    → pself._flatten_final() 카운트:  national_road = 242 (원시)
    → P_self.json marginal = 0.0024
    → analyze §9: P_ext는 road_type 2종뿐(2/4 한계) → 공통지지 {highway,national_road} 재정규화
       self 242/(242+15581)=0.015  vs  ext 0.585(KTDB 구성비)
    → r = 0.015/0.585 ≈ 0.03   ← 헤드라인
  ```
- **아티팩트 가설:** VLM이 국도를 경계 모호로 오분류 가능 — 왕복2차로 국도→`rural`,
  중앙분리대 국도→`highway`. 그러면 242는 실제 수가 아니라 "태거가 국도라 확신한 하한".
- **갈림(조치 정반대):** 진짜 → **수집 편향**(나가서 국도 찍기) / 아티팩트 → **라벨 문제**
  (데이터엔 국도 있는데 다른 이름 → 태거·crosswalk 보정).
- **검증방법(독립 재현):** ① national_road 242장 표본 열어 원본이 정말 국도인지 ② rural/highway
  표본에 국도가 섞였는지 ③ phase0 v1 vs v2 national_road 카운트 일관성 ④ 태거 프롬프트의
  national_road 정의가 rural/highway와 문구상 겹치는지.
- **결과 / 판정 / 조치:** ⬜ **대기 (검증 미실시)**.

## 부록 A — 핵심 단계 코드 워크스루 (검토 참고)

> 로직이 무거운 단계의 코드 동작을 압축 기록. 검토(T2~) 시 근거로 참조. 숫자는 실제 실행값.

### A-1. `compose.py` — P_ext 조립 (§7)

**입력** `loader.load_all()`의 8블록 중 compose가 **쓰는 건 4개뿐**:
```
w_vkt      {(): {highway:0.41465, national_road:0.58535}}          # P(road_type)
w_hourly   {(highway,): {0:0.0124,…,8:0.05521,…}, (national_road,):…}  # P(시각|road_type)
P1_weather {(1,8): {clear:0.9375, rain:0.045, snow:0.0175}, …}     # 288칸
P1_fog     {(1,8): 0.2907, …}                                       # P(안개있음|월,시)
```
speed·agent·density·lighting은 tables에 있지만 **compose가 한 번도 참조 안 함** = 의도적 marginalize.

> **왜 일부러 빼나 (버그·누락 아님):** 이 4블록은 **손앵커**(데이터 없는 추측값)다. P_ext에 넣으면
> §8 핵심영역·§9 과수집 판정이 그 추측에 **오염**되어 신뢰할 수 없게 된다(§13-R 게이트 A: 손앵커
> 축을 고정한 조합은 손 prior를 문다). 그래서 **합쳐 지운다(marginalize)**. 구현이 "루프에서 안
> 곱하기"인 이유: 조건부표는 값 합=1이라 그 축을 전부 더하면 factor가 1이 되어 사라진다 →
> **안 곱하는 것 = 정확히 합쳐 지우는 것**. 덕분에 §8/§9 선정이 손값에 **불변**이고(sweep Part A가
> "손앵커 소스 교란해도 P_ext 12셀 동일"을 assert로 증명), 손앵커 축은 버리는 게 아니라 §10
> criticality·§11 스윕에서 따로 다룬다.

**① `build_strata()` — 주행을 (월·시·도로)로 자른 576 조각과 각 몫(무게)** (2×12×24 = **576** 층)
```
w[(m,h,k)] = P(road_type k) × P(시각 h|k) × 1/12
  예: w[(1월,8시,고속)] = 0.41465 × 0.05521 × 1/12 ≈ 0.00191
```
`/12` = **월 균등 가정**(월별 VKT 없음 → 검토 T2-1). Σ도로=Σ시각=Σ월=1이라 합=1(정규화는 안전장치).

**② `compose()` — 576조각을 각각 날씨3×안개2로 쪼개, 월·시 버린 공통키 12칸에 합산** (코어)
```
for (m,h,k), ws in 576층:
  pf = P1_fog[(m,h)]
  for weather, pw in P1_weather[(m,h)]:      # 맑음/비/눈
    rs = SURFACE[weather]                     # 날씨→노면 결정적(맑음→dry…)
    for fog, pfog in (present:pf, none:1-pf):
      P[(k,weather,fog,rs)] += ws × pw × pfog # 무게×날씨확률×안개확률
```
**목적 — 뭘 만드나:** "현실 주행이 각 `(도로·날씨·안개·노면)` 상황에 **얼마나 노출되나**"를 확률로
적은 표 = **P_ext**. 이게 §8 핵심 운행영역과 §9 과수집 판정의 **현실 기준선**이 된다.
compose가 하는 일은 딱 하나 — `build_strata`가 만든 576조각(='언제·어디서 얼마나 달리나')에
날씨·안개 확률을 곱해, "달린 상황"별 확률로 재배열하는 것.

**한 문장:** 시간·도로로 잘게 나뉜 576조각을 **날씨·안개 상황별로 다시 묶어**, 최종 12칸짜리
"상황별 노출 확률표"로 재정리한다.

**세 단계로 보면 (① 자르기는 build_strata, ②③ 이 함수):**
```
① 자르기        ② 쪼개기            ③ 합치기
576 조각 ──────▶ 576×6 부스러기 ──────▶ 12 칸
(월·시·도로)     (조각마다 날씨3×안개2)   (도로2×날씨3×안개2)
 잘게 자름         더 잘게 나눔           같은 키끼리 몰아 더함
                                        ↑ 월·시 사라짐(줄어듦)
```
- **② 쪼개기(중간, 갈래 늘어남):** 조각 하나(예: 1월8시·고속)를 그 시각의 날씨·안개 확률로
  6갈래로 나눈다. '이 시각 주행 중 얼마가 맑고·비오고·안개끼나'를 확률만큼 갈라 담는 것.
- **③ 합치기(결과, 칸 줄어듦):** 그렇게 나온 부스러기들 중 **최종 키(도로·날씨·안개·노면)가 같은
  것끼리 한 칸에 더한다.** 시각(월·시)은 결과 키에 안 남기니, 언제였든 상황만 같으면 같은 칸으로 모인다.

주의 — ③은 "12칸으로 **분리**"가 아니라 "12칸으로 **합침**"이다. 갈래가 늘었다가(576→576×6),
같은 상황끼리 몰아 더하며 줄어든다(→12). 288개(12월×24시) 시간칸이 도로·날씨·안개로 접혀 12칸만 남음.
"언제 달렸나"를 지우고 "어떤 상황에서 달렸나"로 갈아끼우는 게 이 함수의 전부다.

- **왜 12칸인가:** 우리가 최종으로 알고 싶은 축은 `(도로2·날씨3·안개2)` 셋뿐 → `2×3×2 = 12`.
  노면은 날씨가 결정(맑음→dry·비→wet·눈→snow)하는 **파생값**이라 자유축이 아님 → 칸 수를 안 늘림.
  → **월·시는 최종 관심축이 아니다.** '언제'는 날씨·교통량을 정하려고 잠깐 쓰는 중간 좌표일 뿐,
  결과표엔 안 남긴다. 그래서 월·시가 달라도 나머지 키가 같으면 **한 칸에 합쳐진다**(= 시간축을
  더해 지움 = marginalize):

    1월8시·고속의 '맑음' ┐
    7월15시·고속의 '맑음' ┼─▶ 전부 `(고속, 맑음, none, dry)` **한 칸**에 누적
    3월2시·고속의 '맑음' ┘

- **조각 하나가 겪는 일 (물 붓기 비유):** 조각 `(1월,8시,고속)`을 무게 `ws=0.00191`짜리 물 한 컵으로
  보고, 이 물을 **2번 갈라** 6개 칸에 나눠 붓는다. 물 총량은 갈라도 그대로(합=ws).

```
                         ws = 0.00191    ← 물 한 컵
                               │
  ┌────────────── 1단계: 날씨 확률 pw 로 3덩이 ──────────────┐
  │              (pw = P1_weather[(1월,8시)] 에서 조회)        │
  │                                                          │
 ×0.9375(맑음)              ×0.045(비)              ×0.0175(눈)
  = 0.0017906               = 0.0000860              = 0.0000334
  │                          │                        │
  └ 2단계: 안개 확률 pfog 로 각 덩이를 다시 2조각 (pf=0.2907) ┘
  │                          │                        │
 ┌┴──────────────┐    ┌─────┴──────┐      ┌──────────┴─────┐
none ×0.7093  present ×0.2907   none ×0.7093  present ×0.2907   none ×0.7093  present ×0.2907
```

  1단계에서 `0.00191`이 날씨 비율대로 3덩이로 갈리고(합 그대로), 2단계에서 각 덩이가 안개로 또 2조각
  → 총 **6조각**. 각 조각 크기 = `ws × pw × pfog`. 노면(dry/wet/snow)은 날씨가 결정하니 새로 안 가름.

| # | 목적지 칸 `(도로,날씨,안개,노면)` | 계산 `ws × pw × pfog` | 부을 양 |
|---|---|---|---|
| 1 | (고속, 맑음, none,    dry ) | 0.00191 × 0.9375 × 0.7093 | **0.0012701** |
| 2 | (고속, 맑음, present, dry ) | 0.00191 × 0.9375 × 0.2907 | 0.0005205 |
| 3 | (고속, 비,   none,    wet ) | 0.00191 × 0.045  × 0.7093 | 0.0000610 |
| 4 | (고속, 비,   present, wet ) | 0.00191 × 0.045  × 0.2907 | 0.0000250 |
| 5 | (고속, 눈,   none,    snow) | 0.00191 × 0.0175 × 0.7093 | 0.0000237 |
| 6 | (고속, 눈,   present, snow) | 0.00191 × 0.0175 × 0.2907 | 0.0000097 |
| | | **6조각 합** | **≈ 0.00191** ✓ (=ws, 물 보존) |

  이 6조각을 각 목적지 칸에 **부어 더한다**(`P[c] += 부을 양`). 그리고 이 붓기를 **576조각 전부** 반복
  → 서로 다른 조각의 같은-칸 조각들이 쌓여 최종 12칸 확률이 완성된다.

**왜 이 방식이 맞나 (검토 포인트 5):**
- **상관관계가 공짜:** 날씨확률 `pw`를 조각(월,시)마다 **새로** 조회하니까, 7월 조각은 눈≈0 →
  `한여름×눈` 칸엔 거의 안 부어짐. 계절-날씨 상관을 따로 코딩 안 해도 저절로 현실적으로 나온다.
- **정확 계산(랜덤 아님):** 576×6=3,456갈래를 for로 **전부** 더한다. 몬테카를로 표본추출이 아니라
  전수 합산이라 표본오차 0.
- **손앵커 4축은 아예 안 곱한다:** speed·agent·density·lighting은 추측값(손앵커)이라 P_ext에서 뺀다.
  조건부표는 값 합=1이라 **곱셈에서 빼면 그 축이 1로 합쳐져 사라짐** → 결과는 신뢰 4축만 남음.
- **road_surface는 새 축이 아니다:** 날씨에서 1:1로 결정되는 파생값(맑음→dry…). §9에서 태거 노면과
  대조하려고 키에 실어둘 뿐, 자유도(칸 수)를 늘리지 않는다.
- **왜 "쪼개고 합치는" 우회처럼 보이나 (한 방에 못 하나):** 사실 우회 아님 — `P[c] += …` 단일 패스로
  쪼개기·합치기를 동시에 한다("부스러기"는 실체 없는 서술상 단계). **조각별 곱을 먼저, 합을 나중**에
  하는 순서는 확률론 정석이라 못 줄인다: 미리 marginal로 뭉쳐 곱하면
  `Σ P(w|m,h)P(f|m,h) ≠ ΣP(w)·ΣP(f)` — 날씨-안개의 (시간 매개) **결합/공분산이 소실돼 틀림**.
  루프는 그 상관을 보존하는 장치. 연산 576×3×2≈3.5K(밀리초)라 einsum·인수분해 최적화는 불요·불이득.

**③ `main()`** — `assert 합=1`(무결성) → 내림차순 직렬화 → `output/P_ext.json`.
**`_selfcheck()`** — 합성표로 합=1·최빈셀=clear+dry assert(코어 수식 가드).

**결과 P_ext.json (12셀 = 2도로×3날씨×2안개, 노면은 날씨가 결정):**
```
national_road·clear·none·dry 0.4634 · highway·clear·none·dry 0.3260 · … (합=1)
```
얻는 것: ① §8 핵심영역(상위 5셀=95%) ② §9 비교 기준선(현실 앵커) ③ 손추측 오염 0.
